
本节基于官方文档介绍一下 Claude Code 5月新出的**动态工作流（Dynamic Workflows）**的主干内容，了解一下这个新功能的运行机制，适合什么样的任务。

## 1. 动态工作流解决的问题类型

动态工作流本身运行的时候集合了多种子模块的思想，比如说任务规划、子agent、多agent、后台任务等等，一句话总结就是动态工作流适合解决更大规模更复杂问题而诞生的。

比如一些真实场景：

- **跨整个仓库的迁移**：大代码仓库的迁移成其他语言的时候，每个文件还得有人审、有人跑测试。
- **跨整个服务的 Bug 扫描**：从安全、并发、逻辑、错误处理等多个角度，扫几百个文件，把可疑点都列出来，再交叉验证，再去修。
- **海量内容的横向研究**：一个研究问题分成多个搜索角度，并发抓几十个网页，每条声明都拉若干 Agent 独立反驳，留下一致的结论。

这类任务有几个共同特点：

1. **任务规模远大于一次会话能装下的上下文**。几百个文件的中间结果，往主 Claude 上下文窗口里一塞，注意力立刻被稀释，而且很快就溢出。
2. **结构高度规则化**：扇出（fan-out）→ 各自跑 → 汇合（fan-in）这个模式被反复使用，模式比内容稳定。
3. **协调本身的算力很便宜**：循环 1000 次、把数组 filter 一遍、按文件名分组——这些用 LLM 来做完全是浪费，用一段 JavaScript 跑就行。

对于此类存在重复、任务量大、但又可编排化运行的任务，一个很自然的想法：**让 LLM 不再亲自一轮一轮地"想下一步"，而是先一次性写出一段编排脚本，剩下的事交给一个无脑但确定的运行时去跑**。这就是动态工作流可以解决的问题。

## 2. 核心概念：把"计划"搬进代码

动态工作流的官方一句话定义只有一行：

> **A workflow moves the plan into code.** —— 工作流把计划搬进了代码。

我们在之前章节介绍过，传统模式下agent工作模式是这样的：

```text
想一步 → 派一个 subagent 去做 → 等结果回来 →
读结果 → 想下一步 → 再派一个 ...
```

整套编排逻辑活在 Claude 的"脑子里"，靠一轮又一轮的对话推动。每一次"读结果、想下一步"，都要让模型重新看一眼上下文窗口、重新做一次决策。规模一大，这件事就崩了。

动态工作流改的正是这件事。它让 Claude 在一开始就把"哪里分割出 100 个任务"、"哪里要等齐"、"哪个结果喂给哪个下一步"——这些**编排过程**——一次性写成一段可以执行的 JavaScript 脚本。脚本本身不含任何模型调用，它只是普通的 `for`、`await`、`map`、`filter`，写完就交给本机的一个 JS 运行时去跑。一个JS最简实例如下：

```javascript
// 一个动态工作流脚本的最小骨架
export const meta = {
  name: 'review-codebase',
  description: '多角度代码审查',
  phases: [
    { title: 'Discover', detail: '发现问题' },
    { title: 'Verify',   detail: '验证发现' },
  ],
}

phase('Discover')

// 三个角度并行扫
const findings = await parallel([
  () => agent('从安全角度找问题', { schema: FINDING_SCHEMA }),
  () => agent('从性能角度找问题', { schema: FINDING_SCHEMA }),
  () => agent('从可维护性角度找问题', { schema: FINDING_SCHEMA }),
])

// 注意这一段：filter / flatMap 是普通 JS，不消耗任何 LLM token
const claims = findings.filter(Boolean).flatMap(r => r.items)
log(`共 ${claims.length} 条待验证发现`)
```

在传统 subagent 模式里，三次审查的中间结果都要回到主 Claude 的上下文，让主 Claude 决定下一步；而在 workflow 里，这三次审查的结果只是 JS 变量，被普通的 `filter` 和 `flatMap` 处理，主 Claude 此时正在睡觉。

可以这样总结这个核心转变：

> 编排从"一段对话"变成了"一段程序"。循环、分支、攒中间结果这些事，本来压在 Claude 的注意力上，现在压给了一个无脑但确定性的 JS 运行时。

## 3. 运行模型：主 Claude 休息，脚本在跑

我们再细看一下，从你按下回车到拿到最终结果，这中间到底发生了什么。

```text
┌─────────────────────────────────────────────────────────┐
│ ① 用户发起请求                                           │
│   "用一个 workflow 给整个仓库做安全审计"                    │
└────────────────────┬────────────────────────────────────┘
                     ▼
┌─────────────────────────────────────────────────────────┐
│ ② 主 Claude（这一回合的最后一件事）                         │
│   生成一段 JavaScript 工作流脚本                           │
│   写完 → 交出去 → 自己进入休眠                              │
└────────────────────┬────────────────────────────────────┘
                     ▼
┌─────────────────────────────────────────────────────────┐
│ ③ 本机 JS 运行时（无脑、确定性）                           │
│   · 跑 for / map / filter / await 这些纯 JS              │
│   · 本身不含任何 LLM，给同样输入走同样路径                   │
│   · 中间结果留在脚本变量里，不进任何上下文                    │
│                                                         │
│   ┌──────────┐  ┌──────────┐  ┌──────────┐              │
│   │ agent()  │  │ agent()  │  │ agent()  │ ← 跑到这一行  │
│   │ ↓ LLM    │  │ ↓ LLM    │  │ ↓ LLM    │   才临时雇    │
│   └──────────┘  └──────────┘  └──────────┘   一个子 Agent│
│        ↓             ↓             ↓                    │
│   结果回到脚本变量 → filter / map / 交叉检查                │
│   全部跑完 → 通知主 Claude                                │
└────────────────────┬────────────────────────────────────┘
                     ▼
┌─────────────────────────────────────────────────────────┐
│ ④ 主 Claude 被叫醒                                       │
│   只读最终汇总结果，给用户写一份报告                          │
└─────────────────────────────────────────────────────────┘
```

这里头藏着这套机制最容易被误解的一点：

> Workflow **不是**跑在 Anthropic 服务端的什么编排引擎，它就是 Claude Code 在你**本机**起的一段 JavaScript 脚本，由一个本地 JS 运行时来执行。

理解这一点，很多看起来神奇的能力就一下子合理了。

**为什么能扛住几百个并发 Agent？** 因为真正在外面循环的，是那段不调用模型的 JavaScript。

**为什么主 Claude 的上下文不会爆？** 因为整个 workflow 跑完，主 Claude 拿到的只是最终结果，一个 `return` 出来的小对象，中间几百个 Agent 的输出根本没进它的窗口。

**为什么中断之后还能恢复？** 因为脚本运行进度是落到本地的，不依赖那条对话的内存状态。

**为什么协调成本几乎为零？** 因为那些循环、判断、汇总，本来就不该让 LLM 来做，让 V8（ JavaScript 引擎） 跑就行。

唯一会"花钱"的地方，是脚本里写着 `await agent(...)` 的那几行——只在跑到那行的时候，运行时才临时雇一个有干净上下文的子 Agent 干一件事，干完释放，结果回来变成一个 JS 变量。

我们之前讲过 subagent 的本质："新起一个全新对话窗口、有独立 system prompt、跑完只把摘要带回来"。workflow 里 `agent()` 的语义和那个完全一致——区别只是这次叫它干活的是一段 JS，而不是另一个 LLM。

## 4. 它和系列其他机制的关系

光看上面的描述，可能会有个疑惑：这听起来不就是"加强版的 subagent"或者"换个皮的 Agent 团队"吗？

不完全是。我们把前面几节的机制拉到一起做个横向对比，差别就清晰了：

| 维度 | Session（普通会话） | SubAgent | Skill | Agent Teams | **Workflow** |
| --- | --- | --- | --- | --- | --- |
| 编排者 | 用户 | 主 Claude 逐轮 | 主 Claude 逐轮 | 主 Claude（网状协作） | **JavaScript 脚本** |
| 中间结果存放 | 上下文窗口 | 回到上下文窗口 | 回到上下文窗口 | 队员收件箱 + 上下文 | **脚本变量（堆内存）** |
| 规模量级 | 单次会话 | 一轮派几个 | 一次一条指令 | 几个队员长期共事 | **数十到数百，单次最多 1000** |
| 可重复性 | 低 | 子 Agent 模板复用 | 指令模板复用 | 团队配置复用 | **整套编排逻辑复用** |
| 协作拓扑 | 串行 | 星形（一对多） | 链式 | 网状 | **树状（fan-out → fan-in）** |

这个表重点在"中间结果存放"那一行。前四种机制的中间结果**最终都要回到上下文窗口**——subagent 跑完要回主 Claude 读，team 成员之间通过收件箱通信但每条消息也得进对方上下文。

只有 workflow 是个例外：它把中间结果换了个地方存——存在一段脚本的局部变量里。当任务规模大到上下文装不下的时候，前面四种机制都开始吃力，而 workflow 还能继续往上扩。

所以应该这样理解它的定位:

> Workflow **不是** subagent / skill / team 的替代品，它是补上了它们够不到的那一格——**单个 Agent 一次跑不完、中间结果多到上下文装不下的大任务**。

什么时候用前面几种？日常 80% 的活，照旧。
什么时候才上 workflow？当你写需求时心里冒出一句"这要拆几百个文件分别处理"——那一刻它才登场。

## 5. 基础数据结构详解

动态工作流脚本是普通的 JavaScript，但 Claude Code 在它运行的环境里注入了若干全局函数和对象，构成 workflow 的"基础数据结构（原语）"。我们一个一个拆开看，**这是这一节的核心**。

总共有 8 个原语，按使用频率分两层：

| 层 | 原语 | 作用 |
| --- | --- | --- |
| 第一层（结构骨架） | `meta`、`phase`、`agent`、`parallel`、`pipeline` | 描述工作流形状、定义阶段、雇 Agent、并发与流水线 |
| 第二层（工程能力） | `schema`、`budget`、`log`、`args`、`isolation` | 结构化输出、预算控制、可观测、参数化、文件隔离 |

第一层不掌握 workflow 跑不起来；第二层不掌握 workflow 写不出生产可用的水平。

### 5.1 `meta`：工作流的身份证

每个 workflow 脚本必须 `export` 一个 `meta` 对象。它不是函数，它是这个 workflow 的身份证：

```javascript
export const meta = {
  name: 'fix-bugs',                              // 脚本名
  description: '发现并修复代码中的 bug',          // 一句话描述
  phases: [                                       // 阶段大纲
    { title: 'Discover', detail: '发现 bug' },
    { title: 'Fix',      detail: '修复 bug' },
    { title: 'Verify',   detail: '验证修复' },
  ],
}
```

记一个**硬约束**：`meta` 必须是**纯字面量**——里面不能有变量、函数调用、模板插值。原因是运行时要在脚本真正跑起来之前，就把 `meta` 解析出来给用户看一眼"这个工作流大概要干啥"，所以它必须是静态的。

### 5.2 `phase(title)`：把进度切成大段

一个上百步的工作流如果在进度树里铺平，看起来会非常吓人。`phase()` 的作用是把一段连续的 `agent()` 调用归到同一个阶段下，方便用户折叠/展开。

```javascript
phase('Discover')
// ... 这之后所有 agent() 调用都归到 Discover 阶段

phase('Fix')
// ... 这之后所有 agent() 调用都归到 Fix 阶段
```

`phase()` 只影响 UI 展示，不影响执行顺序。`title` 应该和 `meta.phases` 中的 `title` 一致。

### 5.3 `agent(prompt, opts)`：唯一会调 LLM 的那行

整个 workflow 里**只有这一行**真正会调用大模型，雇一个有干净上下文的子 Agent 来干活：

```javascript
const result = await agent('帮我审查 src/auth.ts 的安全性', {
  label:     'security-review',   // 在进度树里显示的名字
  phase:     'Review',            // 归到哪个阶段
  schema:    FINDING_SCHEMA,      // 强制结构化输出（5.6 节细讲）
  model:     'haiku',             // 路由到哪个模型：haiku / sonnet / opus
  isolation: 'worktree',          // 在独立 git worktree 里跑（5.10 节细讲）
})
```

`agent()` 的语义和我们之前讲的 subagent 是完全对得上的：新起一个干净上下文，给一段 prompt，让它带着自己的工具循环干完，最后只把"最终输出"带回来变成 `result`。

变量 `result` 此刻就是一段普通的 JS 数据，可以往 `array` 里 `push`，可以 `JSON.stringify` 写文件，**不会**占用主 Claude 的上下文。

### 5.4 `parallel(thunks)`：要等齐的并发

当我们要做"三个角度同时审"这种动作时，用 `parallel`：

```javascript
const [security, perf, style] = await parallel([
  () => agent('安全审查', { phase: 'Review' }),
  () => agent('性能审查', { phase: 'Review' }),
  () => agent('风格审查', { phase: 'Review' }),
])
// 三个同时跑，全部完成才继续往下走
```

注意传进去的是一个 thunk 数组（每个元素是 `() => agent(...)`），不是直接的 promise 数组——这样 `parallel` 自己控制何时启动，方便做并发上限和断点恢复。

`parallel` 的特点是**有 barrier**：所有任务都跑完了才往下走。它适合"要拿到全部结果一起看"的场景，比如汇总、去重、打分。

### 5.5 `pipeline(items, ...stages)`：不等齐的流水线

但很多时候我们不需要等齐。比如要给 100 个文件分别做"实现 → 测试 → 审查"三步，我们希望 `auth.ts` 在做测试的时候，`db.ts` 已经能开始实现下一阶段了——这就是 `pipeline`：

```javascript
const results = await pipeline(
  ['auth.ts', 'db.ts', 'api.ts'],                          // 要处理的项
  (prev, file) => agent(`实现 ${file} 的功能`),             // Stage 1: 实现
  (prev, file) => agent(`为 ${file} 写测试`),               // Stage 2: 测试
  (prev, file) => agent(`审查 ${file} 的代码质量`),          // Stage 3: 审查
)
```

每个 stage 回调拿到的 `prev` 是同一个 item 在上一阶段的产出，可以一路串下去。

`pipeline` 和 `parallel` 的差别就一个——是否有 barrier：

| 原语 | 有 barrier？ | 总耗时 | 适用场景 |
| --- | --- | --- | --- |
| `parallel([thunk1, thunk2, ...])` | ✅ 有 | = 最慢的那个 thunk | 必须等齐才能下一步（汇总、去重、打分） |
| `pipeline(items, stage1, stage2, stage3)` | ❌ 无 | ≈ 单条最慢链路 | 各 item 独立推进，**默认选择** |

举个例子。三个文件 `auth.ts / db.ts / api.ts`，每个都要走"实现 → 测试 → 审查"。

如果你写成 barrier 风格：阶段 1 三个并行实现等齐 → 阶段 2 三个并行测试等齐 → 阶段 3 三个并行审查等齐。总耗时 = `max(impl) + max(test) + max(review)`。

如果你用 pipeline：`auth.ts` 实现完就开始测试，测试完就开始审查；`db.ts` 同时也在按自己节奏推进；`api.ts` 同样。总耗时 ≈ `max(单条完整链路)`，往往比 barrier 风格快 30–50%，而且任何一个文件出错只影响它自己。

**经验法则**：默认用 `pipeline`，只有当你**确实需要前一阶段的全部结果**才换成 `parallel`。

### 5.6 `schema`：把"解析文本"这件事彻底删掉

`schema` 是一个标准 JSON Schema。带它的时候，运行时会在 LLM 输出回来后做一次结构化校验，校验不过就要求 agent 重新输出，直到拿到合法 JSON 为止。**这是动态工作流和"自己写 JS 调 API"最根本的区别之一**——你写编排脚本时，可以假设每个 `agent()` 的返回都是干净的、已经被校验过的结构化数据。如一个例子：

```javascript
const BUG_SCHEMA = {
  type: 'object',
  properties: {
    bugs: {
      type: 'array',
      items: {
        type: 'object',
        properties: {
          id:    { type: 'string' },
          file:  { type: 'string' },
          line:  { type: 'number' },
          title: { type: 'string' },
        },
        required: ['id', 'file', 'title'],
      },
    },
  },
  required: ['bugs'],
}

// agent() 返回的就是已经被运行时校验过的 JS 对象，不用再 try/catch 解析文本
const result = await agent('找出代码中的所有 bug', { schema: BUG_SCHEMA })
for (const bug of result.bugs) {
  // 直接用 bug.file / bug.line，绝不可能是别的形状
}
```



### 5.7 `budget`：写"边花边干"的循环

回顾《定时调度》，我们讨论过任务的"无限触发"问题。在 workflow 里同样存在：循环到底跑几轮？答案是 **`budget` 对象**。

```javascript
const findings = []

// budget.total 是这次 workflow 的总 token 预算，由调用方传入
// budget.remaining() 是当前还剩多少
while (budget.total && budget.remaining() > 50_000) {
  const result = await agent('深入分析下一个模块', { schema: ANALYSIS_SCHEMA })
  findings.push(...result.items)
  log(`已发现 ${findings.length} 项, 剩余预算 ${Math.round(budget.remaining() / 1000)}k tokens`)
}
```

`budget.total` 为 null 时 `remaining()` 返回 `Infinity`，循环不受预算约束（这时候你最好自己有别的退出条件）。这种"边花边干"的写法很适合**规模未知的探索任务**——预算用完之前能挖多深就挖多深，绝不会失控。

### 5.8 `log`：让进度可见

```javascript
log(`已完成 ${count}/10 个文件`)
```

`log` 不是 `console.log`。它把消息打到 workflow 的进度树上方，用户在 `/workflows` 里能实时看见。这一点很关键——workflow 经常要跑几十分钟到几小时，没有 log 就是黑盒，有了 log 就是可观测系统。

### 5.9 `args`：把工作流变成参数化模板

```javascript
// 脚本里
const feature = args?.feature || 'unknown'
const result = await agent(`实现 ${feature} 功能`)

// 调用时
Workflow({ name: 'feature-impl', args: { feature: '用户认证' } })
```

`args` 让一个工作流变成一个**带参数的子程序**。这对应了我们一直强调的"复用维度"——subagent 复用一个工作者、skill 复用一条指令、workflow 复用**整套编排逻辑**。把脚本保存到 `.claude/workflows/` 之后，未来任何一次会话都可以 `/feature-impl 用户认证` 一行触发，而背后跑的是一整套你精心设计的多阶段流程。

### 5.10 `isolation: 'worktree'`：并行改文件不冲突

这一项和《工作树与任务隔离》相似。当多个 Agent 要并行修改同一个仓库的文件时，最可怕的事情就是它们写花了——A 的修改盖住 B 的，B 又没看到 A 的依赖。

```javascript
const result = await agent('实现登录模块', {
  isolation: 'worktree',  // 在独立 git worktree / 分支中跑
})
```

加上 `isolation: 'worktree'`，运行时会自动给这个 Agent 开一个独立的 git worktree，相当于给它一个干净的工位。

## 6. 常见 5 种编排范式

原语就那 8 个，但拼起来可以组合出形形色色的编排模式。我们挑出工程实战中最反复出现的 5 种讲讲。

### 6.1 范式 1：对抗性验证（Adversarial Verify）

LLM 的一个问题是"看似正确实则错误"——它给出一个结果，听起来头头是道，实际上是幻觉。怎么办？让 N 个独立的 Agent 尝试**反驳**这个发现，多数反驳成功就剔除。

```javascript
const VERDICT_SCHEMA = {
  type: 'object',
  properties: {
    refuted: { type: 'boolean' },
    reason:  { type: 'string' },
  },
  required: ['refuted', 'reason'],
}

const votes = await parallel([
  () => agent(`尝试反驳：${claim}。如果不确定，默认 refuted=true。`, { schema: VERDICT_SCHEMA }),
  () => agent(`尝试反驳：${claim}。如果不确定，默认 refuted=true。`, { schema: VERDICT_SCHEMA }),
  () => agent(`尝试反驳：${claim}。如果不确定，默认 refuted=true。`, { schema: VERDICT_SCHEMA }),
])

// 至少 2/3 认为无法反驳，才保留
const survives = votes.filter(Boolean).filter(v => !v.refuted).length >= 2
```

两个细节值得品。第一，**默认值偏保守**——"如果不确定就当作 refuted=true"，宁可错杀也不要放过。第二，**3 个 Agent 跑的是同一个 prompt**，但它们的随机性相互独立，所以多数投票本身就是一种降噪。

### 6.2 范式 2：循环直到达标（Loop-until-dry）

面对"代码库里到底有多少 bug"这种**规模未知**的任务，你写不出一个"跑 N 轮就够"的常量。那就让它跑到没东西可挖为止：

```javascript
const bugs = []
const seen = new Set()
let consecutiveEmpty = 0

while (consecutiveEmpty < 2 && budget.remaining() > 100_000) {
  const result = await agent('找出代码中尚未发现的 bug', { schema: BUGS_SCHEMA })
  const newBugs = result.bugs.filter(b => !seen.has(b.id))

  if (newBugs.length === 0) {
    consecutiveEmpty++
  } else {
    consecutiveEmpty = 0
    bugs.push(...newBugs)
    newBugs.forEach(b => seen.add(b.id))
  }
  log(`已找到 ${bugs.length} 个 bug，连续空轮 ${consecutiveEmpty}`)
}
```

退出条件是"连续 K 轮没有新发现"，配合 `budget.remaining()` 兜底防止跑飞。这是探索性任务最稳妥的写法。

### 6.3 范式 3：多视角评审（Judge Panel）

需要做一个开放性决策（设计方案、文案选型、API 设计）时，单个 Agent 容易陷在自己的视角里。让多个 Agent 从不同角度独立提方案，再让一组评委打分：

```javascript
// 三个 Agent 从不同角度提方案
const approaches = await parallel([
  () => agent('从 MVP 角度设计方案：能跑就行',     { phase: 'Design' }),
  () => agent('从安全性角度设计方案：纵深防御',     { phase: 'Design' }),
  () => agent('从用户体验角度设计方案：丝滑无感',   { phase: 'Design' }),
])

// 评委独立打分
const scores = await parallel(
  approaches.map(a => () =>
    agent(`评估这个方案：\n${a.summary}`, {
      phase: 'Judge',
      schema: { type: 'object', properties: { score: { type: 'number' } }, required: ['score'] },
    })
  )
)

// 选最高分
const winnerIdx = scores.map(s => s.score).indexOf(Math.max(...scores.map(s => s.score)))
const winner = approaches[winnerIdx]
```

注意提方案和打分**严格隔离**——提方案的 Agent 不知道有评委，打分的 Agent 不知道方案是谁出的。这样才不会互相影响。

### 6.4 范式 4：多维度扫描（Multi-modal Sweep）

一个维度一个 Agent，全部并行扫一遍。代码审查就是经典场景：

```javascript
const DIMENSIONS = [
  { key: 'security',        prompt: '审查安全性：SQL 注入、XSS、硬编码密钥、越权' },
  { key: 'performance',     prompt: '审查性能：N+1 查询、内存泄漏、不必要的重渲染' },
  { key: 'maintainability', prompt: '审查可维护性：代码重复、过长函数、深层嵌套' },
  { key: 'testing',         prompt: '审查测试覆盖：缺失的边界用例、未覆盖的错误分支' },
]

const reviews = await parallel(
  DIMENSIONS.map(d => () =>
    agent(d.prompt, {
      label: `review:${d.key}`,
      phase: 'Review',
      schema: FINDING_SCHEMA,
    })
  )
)
```

这种范式的好处：**每个 Agent 只关心一件事**，prompt 短、噪音小、输出聚焦。一个让一个 Agent 做八件事的 prompt，输出质量永远比不过八个各做一件事的 Agent。

### 6.5 范式 5：Pipeline 默认优于 Barrier

这一条不是新范式，而是写 workflow 的**第一原则**。

**决策规则**：默认 `pipeline`。只有当你确实需要"前一阶段全部结果"才能进下一阶段（去重、汇总、打分、选最优）时，才换 `parallel` barrier。

为什么这条单独拎出来？因为它直接影响 workflow 的总耗时和成本。你只要在写脚本时多问自己一句"我真的需要等齐吗"，就能省下一大把时间和 token。

## 7. 完整示例：Bug 修复工作流

把上面 8 个原语和 5 种范式串起来，看看一个完整的 workflow 长什么样。

这里以一个具体例子为例，任务是：在一个仓库里发现并修复 bug，最后跑通 typecheck 和测试。

三个阶段：**Discover → Fix → Verify**。Discover 用范式 4 多维度并行找 bug；Fix 用 pipeline 让每个 bug 各自推进；Verify 用一个 Agent 跑最终验证。

```javascript
// ─────────── meta ───────────
export const meta = {
  name: 'fix-bugs',
  description: '发现并修复代码中的 bug',
  phases: [
    { title: 'Discover', detail: '从 3 个角度并行找 bug' },
    { title: 'Fix',      detail: '逐个 bug 用 pipeline 修复' },
    { title: 'Verify',   detail: '运行 typecheck 与测试，确认' },
  ],
}

// ─────────── 共享 schema ───────────
const BUG_SCHEMA = {
  type: 'object',
  properties: {
    bugs: {
      type: 'array',
      items: {
        type: 'object',
        properties: {
          id:          { type: 'string' },
          title:       { type: 'string' },
          file:        { type: 'string' },
          line:        { type: 'number' },
          description: { type: 'string' },
          fix:         { type: 'string' },
        },
        required: ['id', 'title', 'file', 'description', 'fix'],
      },
    },
  },
  required: ['bugs'],
}

// ─────────── Discover：3 个角度并行 ───────────
phase('Discover')

const searches = await parallel([
  () => agent(
    '从错误处理角度找 bug：未捕获的异常、空指针、类型错误',
    { label: 'search:error-handling', phase: 'Discover', schema: BUG_SCHEMA, model: 'haiku' }
  ),
  () => agent(
    '从并发角度找 bug：竞态条件、死锁、资源泄漏',
    { label: 'search:concurrency',    phase: 'Discover', schema: BUG_SCHEMA, model: 'haiku' }
  ),
  () => agent(
    '从逻辑角度找 bug：边界条件、off-by-one、错误的条件判断',
    { label: 'search:logic',          phase: 'Discover', schema: BUG_SCHEMA, model: 'haiku' }
  ),
])

// 用 file:line:title 做去重 key
const seen = new Set()
const bugs = searches
  .filter(Boolean)
  .flatMap(r => r.bugs)
  .filter(b => {
    const key = `${b.file}:${b.line}:${b.title}`
    if (seen.has(key)) return false
    seen.add(key)
    return true
  })

log(`发现 ${bugs.length} 个唯一 bug，开始进入 Fix 阶段`)

// ─────────── Fix：pipeline 逐个修复 ───────────
phase('Fix')

const fixes = await pipeline(
  bugs,
  (_, bug) => agent(
    `修复以下 bug：\n` +
    `文件: ${bug.file}:${bug.line}\n` +
    `问题: ${bug.title}\n` +
    `描述: ${bug.description}\n` +
    `建议修复方案: ${bug.fix}\n\n` +
    `请实现修复，然后运行 pnpm typecheck 自查通过。`,
    {
      label:     `fix:${bug.id}`,
      phase:     'Fix',
      isolation: 'worktree',  // 每个 bug 在独立 worktree，避免互相覆盖
      model:     'sonnet',    // Fix 阶段用更强模型
    }
  )
)

// ─────────── Verify：最终一个 Agent 总验证 ───────────
phase('Verify')

const verification = await agent(
  `验证所有 bug 修复：\n` +
  `1. 合并所有 worktree 中的修复\n` +
  `2. 运行 pnpm typecheck\n` +
  `3. 运行 pnpm test\n` +
  `4. 确认以下文件的修复：${bugs.map(b => b.file).join(', ')}`,
  {
    label: 'final-verify',
    phase: 'Verify',
    model: 'opus',  // Verify 阶段用最强模型，关键决策不能错
    schema: {
      type: 'object',
      properties: {
        typecheckPassed:  { type: 'boolean' },
        testsPassed:      { type: 'boolean' },
        allFixesVerified: { type: 'boolean' },
        notes:            { type: 'string' },
      },
      required: ['typecheckPassed', 'testsPassed', 'allFixesVerified'],
    },
  }
)

return {
  bugsFound:    bugs.length,
  bugsFixed:    fixes.filter(Boolean).length,
  verification,
}
```

这段脚本不长，但几乎把这一节讲过的所有原语和范式都用了一遍，注意几个工程上的小细节：

- **三个阶段路由不同模型**：Discover 用 haiku（量大、便宜），Fix 用 sonnet（要写代码），Verify 用 opus（最终决策）。这样子可以控制 token 成本。
- **Fix 阶段加 `isolation: 'worktree'`**：多个修复并行进行时，给每个修复一个独立工位，最后再合并。
- **去重靠 `file:line:title` 复合 key**：三个 search Agent 极有可能找到同一个 bug，必须去重，否则后面 Fix 阶段会把同一个文件改三次。这一行去重是普通 JS 做的，**不消耗任何 token**。
- **Discover 用 `parallel` barrier**：因为去重必须拿到全部三个搜索结果才能做。
- **Fix 用 `pipeline`**：每个 bug 各跑各的，第一个修完不必等其他人。
- **schema 兜底**：每个 `agent()` 都有 schema，最终的 `verification` 直接就是结构化对象，主 Claude 拿到就能用。

这就是一个"可读、可改、可复用"的生产级 workflow 应有的样子。把这段代码保存到 `.claude/workflows/fix-bugs.js`，未来任何一次会话都可以一行 `/fix-bugs` 触发整套流程。

## 8. 运行约束与成本控制

workflow 的能力强但是也是非常耗token的。有几个硬约束很关键：

| 约束 | 详情 |
| --- | --- |
| **最大并发 Agent** | `min(16, CPU 核数 - 2)`，本机 CPU 决定 |
| **单次 workflow 最多 Agent 数** | **1000 个**（防止失控循环烧 token） |
| **运行时间** | 没有硬上限，但有 budget 兜底 |
| **中途用户输入** | 不可，仅权限提示能暂停 |
| **脚本本身** | 没有文件系统/Shell 访问，只能通过 `agent()` 调度 Agent 来读写 |
| **meta 必须是纯字面量** | 不能有变量、函数调用、模板插值 |

成本控制有四个杠杆：

1. **不同阶段路由不同模型**：Discover/扫描类用 `haiku`，写代码用 `sonnet`，关键决策用 `opus`。前面 fix-bugs 例子省了大约一半 token。
2. **`budget.remaining()` 兜底循环**：所有 while 循环都加上预算判断，再加上"连续 K 轮无新发现"双保险。
3. **去重在脚本里做，别让 LLM 做**：JS 一行 `Set` 解决的事，不要交给 Agent。
4. **`/workflows` 按 `p` 暂停、按 `x` 停止**：跑偏了立刻停，已完成的 Agent 结果不会丢。

> Anthropic 在官方建议里特意强调：**workflow 的 token 消耗远超普通 Claude Code 会话**，第一次跑请从小范围任务起步，先观察一次大概烧多少。

## 9. 何时该用 / 不该用

| 场景 | 选择 |
| --- | --- |
| 简单单文件修改 | ❌ 不要用 workflow，直接对话 |
| 每一步都要你拍板 | ❌ 不要用，workflow 是无人值守的 |
| 多个 Agent 抢同一片文件，但你没拆清边界 | ❌ 容易写花，先拆模块再上 |
| 跨整个代码库的审计、迁移、重构 | ✅ 典型场景 |
| 高风险决策需要多角度对抗性验证 | ✅ 用范式 1 |
| 规模未知、要循环到收敛的探索任务 | ✅ 用范式 2 + budget |
| 一次对话上下文装不下、中间结果海量 | ✅ workflow 的主战场 |
| 团队里反复跑的高价值流程（安全审计、发布前 review、迁移预检） | ✅ 沉淀进 `.claude/workflows/`，变成 slash command |

最后一行尤其值得强调——**把 workflow 写一次，存下来，团队所有人都能用**。这才是 workflow 真正的复利所在。

## 10. 小结

我们这一节把动态工作流从"是什么"一路讲到了"怎么用"。浓缩一下：

1. **要解决的问题**：单 Agent 一次跑不完、中间结果上下文装不下的大任务。subagent / skill / agent teams 够不到的那一格。
2. **核心转变**：A workflow moves the plan into code——编排逻辑从"一段对话"变成了"一段在你本机跑的 JavaScript"。主 Claude 写完脚本就休眠，循环和聚合交给无脑确定性的 JS 运行时，只在 `agent()` 那一行才临时雇 LLM。
3. **8 个原语**：`meta`、`phase`、`agent`、`parallel`、`pipeline` 是结构骨架；`schema`、`budget`、`log`、`args`、`isolation` 是工程能力。
4. **5 种范式**：对抗性验证、loop-until-dry、judge panel、多维度扫描、pipeline 默认优于 barrier。
5. **一个完整例子**：`fix-bugs` workflow——Discover 多角度并行扫、Fix pipeline 逐个修、Verify 最终把关，三阶段三档模型，去重靠 JS 不靠 LLM。

回头看看基础的agent_loop。当时我们写的 agent_loop 是 LLM 自己在循环里反复问"下一步干什么"，每一轮都要把整个上下文喂回去。从那一刻起，整个系列其实都在围绕同一个矛盾打转：**LLM 的注意力是稀缺资源，怎么不让它被无关的循环和中间状态稀释**。

上下文压缩、记忆系统、任务系统、工作树隔离、MCP，每一节都是这个矛盾的一种解法。

而 workflow 给出的解法最激进——**它干脆把循环从 LLM 里搬出来，搬到一个无脑、确定性、便宜的 JS 运行时里**。LLM 只在那一行 `agent()` 临时露一面，干完就走。这是 agent 工程化路线上的一个重要拐点。

无论后面agent怎么演化，**"把循环搬出 LLM"这个原则会反复出现**。它是 agent 工程的一个底层重力。
