# s17_团队自主代理

上节我们讲了团队协议，本节继续深入探索Agent团队模式的一些功能。

## 1. 团队成员自主代理

之前的团队协作模式面向的角色主要有两类，一类是leader，一类是普通成员，普通成员的任务需要leader来安排，员工一旦完成某个子任务之后，那么这个普通员工就处于下线状态，除非leader再次给他安排新任务唤起。

本节的一个主要思想是，对于刚完成任务的员工其处于空闲状态，空闲的员工并不是立马下线，而是处于监控运行状态，轮询扫描是否有可以认领的工作，而不是等待领导的每一个分配。这里的团队成员是长期工作者，不是只返回单个摘要的一次性子代理。

当然，一个处于监控状态的空闲员工，在后台运行也是需要占用资源的，所以也会有一些时间周期限制，比如可以设置常驻监控时间，到达一定时间之后，还没有可认领的任务，就自动完全下线。

所以对比上节讲的Agent的团队模式来说，本节最大的区别就是Leader在发布任务的时候，可以不用显性的指定非得某个成员来完成这个任务（当然指定更好），普通成员在没有活干的时候，如果他处于监控状态，那么他就会自己找活干。

## 2. 团队成员的运行状态

增加了团队成员的自主代理功能，那么一个团队成员在Agent中的一个运行流程可以如下：

```python
+--------+      Lead 调用 spawn_teammate
| spawn  |
+---+----+
    |
    v
+--------+  tool_use   +--------+
| WORK   | <-----------| LLM    |  处理消息、调用工具
+---+----+             +--------+
    |
    | stop_reason != tool_use 或 调用 idle 工具
    v
+--------+      每 5 秒轮询，最长 60 秒
| IDLE   |
+---+----+
    |
    +---> 收件箱有新消息? -----------> 恢复 WORK
    |
    +---> 任务板有未认领任务? -------> claim + 恢复 WORK
    |
    +---> 超时 60 秒无活动? ---------> shutdown
    |
    +---> 收到 shutdown_request? ---> shutdown
```

对应到自主代理的部分`IDLE`这块，当一个成员确认没有任务处于空闲的时候，那么就变成一个常驻扫描的一个任务去认领新的任务。

| 当前状态 | 触发条件 | 下一状态 |
|----------|----------|----------|
| `spawn` | `spawn_teammate` 调用 | `working` |
| `working` | `stop_reason != tool_use` | `idle` |
| `working` | 调用 `idle` 工具 | `idle` |
| `working` | 收到 `shutdown_request` | `shutdown` |
| `idle` | 收件箱有新消息 | `working` |
| `idle` | 认领新任务 | `working` |
| `idle` | 超时 60 秒 | `shutdown` |
| `idle` | 收到 `shutdown_request` | `shutdown` |
| `shutdown` | Lead 再次 `spawn` | `working` |

## 3. 团队成员的内循环详细

有了上述的描述之后，我们可以把一个团队成员的内部循环核心描述为两个步骤：
* Working阶段
* idle阶段

### 3.1 working阶段

该阶段则表明一个成员正在执行一个子任务，该模块和上节的类似，存在一个最大次数的主循环，在该循环内完成子任务。

核心流程简化如下:
```
while True:
    # ========== WORK PHASE ==========
    self._set_status(name, "working")
    for _ in range(50):  # 最多50次迭代，防止死循环
        inbox = BUS.read_inbox(name)
        for msg in inbox:
            if msg.get("type") == "shutdown_request":
                self._set_status(name, "shutdown")
                return
            messages.append({"role": "user", "content": json.dumps(msg)})
        # ... LLM 调用 ...
        if response.stop_reason != "tool_use":
            break  # 正常完成，退出WORK阶段进入IDLE阶段
        # ... 工具执行 ...
        if idle_requested:
            break  # Agent请求进入idle

    # ========== IDLE PHASE ==========
    # 此处为轮巡找活的过程
```
working 阶段有两个退出路径：
* 自然完成（LLM 不再调用工具）
* 主动声明（Agent 调用 idle 工具）。50 次迭代上限防止死循环。

### 3.2 idle阶段


```
while True:
    # ========== WORK PHASE ==========
    # --------

    # ========== IDLE PHASE ==========
    self._set_status(name, "idle")  # 标记为空闲状态
    resume = False
    polls = IDLE_TIMEOUT // max(POLL_INTERVAL, 1)  # 计算总轮询次数
    for _ in range(polls):
        time.sleep(POLL_INTERVAL)  # 睡眠等待
        # 检查是否有新消息
        inbox = BUS.read_inbox(name)
        if inbox:
            # 按照正常接受任务的方式处理新任务
            break  # 有消息，恢复工作

        # 检查是否有可认领的任务
        unclaimed = scan_unclaimed_tasks(role)
        if unclaimed:
            task = unclaimed[0]
            claim_result = claim_task(
                task["id"], name, role=role, source="auto"
            )
            if claim_result.startswith("Error:"):
                continue  # 认领失败（如已被别人抢走），继续轮询
            # 自动认领成功，构建任务提示
            task_prompt = (
                f"<auto-claimed>Task #{task['id']}: {task['subject']}\n"
                f"{task.get('description', '')}</auto-claimed>"
            )
            ensure_identity_context(messages, name, role, team_name)
            messages.append({"role": "user", "content": task_prompt})
            messages.append({"role": "assistant", "content": f"{claim_result}. Working on it."})
            resume = True
            break  # 有任务，恢复工作

    # 超过IDLE_TIMEOUT没有任何活动 → 优雅关闭
    if not resume:
        self._set_status(name, "shutdown")
        return
    self._set_status(name, "working")  # 恢复工作状态
```

可以看到在IDLE阶段，主要也包括两个过程:
* 检查收件箱看是否有指派的任务
* 扫描任务板看是否有可以做的任务

每次轮询先检查收件箱再检查任务板，确保消息响应优先于任务认领。认领失败（如并发冲突）时 continue 继续轮询，不会误判为无工作可做。

## 4. 其他的细节

大的流程基本上就是这样，当然代码里面具体实现起来的时候，还有很多细细节。比如说：

* 多个成员同时接任务
当项目一大的时候，可能同时会有很多的成员处于空闲状态可以自由地接任务，那么当一个任务发布以后，被多个成员接受怎么办呢？这个时候会有一个锁功能来保证它只被一个成员所接。

* 成员子agent上下文被压缩
设想一下，假如一个子Agent运行时间比较久了，该子Agent的上下文就会比较长，当长到一定程度就会触发上下文的压缩，而每一个子agent的promote里面可能涉及到了对该Agent功能角色的定义，这样时候就需要一种恢复机制来确保这个Agent的角色定义。
