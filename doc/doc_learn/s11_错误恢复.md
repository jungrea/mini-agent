# s11_错误恢复

我们在与大模型对话的过程中，经常会出现一些未知的错误，比如说连接失败，比如说输出太长等等，出现错误了，如何在下一次重启之后恢复也是一个比较重要的问题。本节主要聚焦于错误恢复这块。

## 1. Agent都可能发生那些错误

Agent的错误类型有很多种，我们参考原教程只列举以下几类高频的错误：
```text
1. 输出被截断
   模型还没说完，但 token 用完了

2. 上下文太长
   请求装不进模型窗口了

3. 临时连接失败
   网络、超时、限流、服务抖动
```

输出被截断，举个例子你想让大模型输出一个特别复杂且长的代码，这个时候就很容易导致Token输出用完而出现错误。

上下文太长的意思就是在我们进行了很多轮对话以后，当前的prompt已经非常长了，当然，针对这个问题，我们之前讲过的上下文压缩方法，其实能够解决一定的问题，这里解决方案其实和那里的类似，也是当上下文太长的时候进行压缩。

另外就是比较高频的临时连接失败的问题。那这个就是各大模型厂商在提供服务的时候，会存在网络抖动之类的导致。这种情况一般我们只需要多次尝试请求即可。

具体的对应 3 条恢复路径：

```text
LLM call
  |
  +-- stop_reason == "max_tokens"
  |      -> 注入续写提示
  |      -> 再试一次
  |
  +-- prompt too long
  |      -> 压缩旧上下文
  |      -> 再试一次
  |
  +-- timeout / rate limit / transient API error
         -> 等一会儿
         -> 再试一次
```

## 2. 异常的处理办法

这里的异常处理方法其实和我们常规的代码里面处理异常的办法比较类似，直接使用try catch的方式捕获异常，并在异常中处理。框架就是：

``` python
for attempt in range(MAX_RECOVERY_ATTEMPTS + 1):
    try:
        response = client.messages.create(
            model=MODEL, system=SYSTEM, messages=messages,
            tools=TOOLS, max_tokens=8000,
        )
        break  # success

    except APIError as e:
        xxx

    except:
        xxx
```
这里有一个最大的重试次数，那么在每次重试中，我们进行请求并捕获相关的异常类型。

### 2.1 超时或者请求异常

如果是超时或者其他类型的请求异常，这个时候 `anthropic` 的 sdk 本身已经定义了一些异常类型：`APIError`, 通过产生这种异常类型的内部匹配来处理：

比如说：
```
except APIError as e:
    error_body = str(e).lower()

    # Strategy 2: prompt_too_long -> compact and retry
    if "overlong_prompt" in error_body or ("prompt" in error_body and "long" in error_body):
        print(f"[Recovery] Prompt too long. Compacting... (attempt {attempt + 1})")
        messages[:] = auto_compact(messages)
        continue

    # Strategy 3: connection/rate errors -> backoff
    if attempt < MAX_RECOVERY_ATTEMPTS:
        delay = backoff_delay(attempt)
        print(f"[Recovery] API error: {e}. "
              f"Retrying in {delay:.1f}s (attempt {attempt + 1}/{MAX_RECOVERY_ATTEMPTS})")
        time.sleep(delay)
        continue

    # All retries exhausted
    print(f"[Error] API call failed after {MAX_RECOVERY_ATTEMPTS} retries: {e}")
    return
```

像这里就解决了Promote过长连接失败，网络问题的异常。

### 2.2 输出过长的问题

上面这种异常其实比较好理解，也好处理。那么当输出过长的时候要怎么办呢？如何让大模型在下一次紧接着上次的输出基础上再输出呢？

首先输出过长在SDK的返回码里面是有一个特殊标识的：
`if response.stop_reason == "max_tokens":`
这个输出码就代表着大模型告诉了你当前大模型的输出没有说完。

那么在解析的时候碰到了`stop_reason = "max_tokens"`,我们就给大模型人为的注入一段信息，来提醒大模型下一次直接从截断的位置开始输出：
```
CONTINUATION_MESSAGE = (
    "Output limit hit. Continue directly from where you stopped -- "
    "no recap, no repetition. Pick up mid-sentence if needed."
)
```
* no recap, no repetition：不要总结回顾、不要重复前文
* Pick up mid-sentence if needed：必要时直接衔接没写完的半句，不用另起开头

```
if response.stop_reason == "max_tokens":
    xxx
    messages.append({"role": "user", "content": CONTINUATION_MESSAGE})
```
通过**将这一段关键的信息注入到Message里面**，带入到下一轮请求的对话当中。那么大模型就会按照之前截断的数据来回复。

当然这里还有一些细节，比如说在`stop_reason = "max_tokens"`的这一轮对话中，如果有工具的调用，那么应该让工具的调用放在这个代码的前面先执行，避免某个工具输出量非常大，因为 LLM 可能在一次响应中既调用了工具，又因为 max_tokens 被截断。如果先处理 max_tokens 注入续写消息，工具调用就被跳过了——LLM 下一轮不知道工具结果，可能导致重复调用或逻辑断裂。

因此正确的逻辑是：先执行所有工具 → 再处理 max_tokens，确保工具结果不丢失。

## 3. 简单总结

三种恢复策略可以总结为：
| 策略 | 触发条件 | 恢复方式 | 重试上限 |
| --- | --- | --- | --- |
| **策略1 max_tokens 恢复** | `stop_reason == "max_tokens"` | 注入续写消息，让 LLM 从断点继续 | 3 次 |
| **策略2 prompt 过长恢复** | API 返回 `overlong_prompt` 错误 | 调用 `auto_compact()` 压缩历史后重试 | 3 次（共享重试池） |
| **策略3 网络/限流恢复** | `APIError` / `ConnectionError` / `TimeoutError` | 指数退避 + 随机抖动，等待后重试 | 3 次 |

对比下有无错误恢复的情况下，用户的感觉：

| 维度 | ❌ 无恢复 | ✅ 有恢复 |
| --- | --- | --- |
| 长输出 | 截断即丢失，用户看到不完整内容 | 自动续写，内容完整 |
| 上下文溢出 | API 报错 → 会话终止 | 自动压缩 → 继续对话 |
| 网络抖动 | 一次失败 → 退出 | 指数退避 → 最终成功 |
| 限流 (429) | 直接报错退出 | 等待后重试 |
| 用户体感 | 频繁崩溃，需手动重启 | 几乎无感知，自动恢复 |
| 代码复杂度 | 简单（无 `try/except`） | 略高（需要策略分支） |
| 适用场景 | 演示/Demo | 生产环境 |

整体来说，有了错误恢复，可以让整个程序显得更加的鲁棒，用户的体验也更加的好。
