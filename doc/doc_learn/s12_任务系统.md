# s12_任务系统

我们知道对于Agent来说，当上下文对话内容一长的时候，agent的处理能力就会出现一定程度的漂移，表现在出现幻觉或者理解能力下降，那么任务系统是一个解决任务过长之后，处理能力下降的一个方法之一。

## 1. 什么是任务系统

说到任务系统，其实和我们之前的一个章节，**列任务模式**非常的相似，两者的区别主要体现在：
* **列任务模式**是单次对话内的任务编排，防止单次任务要做的事情太多出现漂移现象，因此在一次对话中开始执行的时候设置好步骤，让大模型严格按照步骤执行；无法跨对话执行，无法跨新对话框执行，无法重启后继续执行；
* **任务系统**是一个在内存磁盘层面留存设计的任务模型，你可以理解为将列任务模式的任务列表存储到了内存中，整个任务状态存储在磁盘上（.tasks/ 目录），而非对话上下文中。因此任务不受上下文压缩（context compaction）影响，能够跨会话持久化存活。这是"持久化工作图"，而非运行时执行槽位。

这是对比我们之前说的列任务模式的区别，那么直接对比有无任务系统的区别可以如下：

| ❌ 没有任务系统 | ✅ 有任务系统 |
| :--- | :--- |
| 任务目标仅存在于对话上下文中 | 任务以 JSON 文件持久化到磁盘 |
| 上下文压缩后，任务信息丢失 | 上下文压缩不影响任务状态 |
| 无法跨会话追踪进度 | 新会话可随时查询和恢复进度 |
| 依赖关系靠人工记忆维护 | 依赖图自动解析和清理 |
| 新会话必须从头描述工作状态 | 任务完成时自动解除下游阻塞 |

## 2. 任务系统的数据设计

可落磁盘的任务系统，在功能上也是更加灵活丰富，比如说有更完整的任务依赖与被依赖的关系，有更详细的任务描述，有更完整的任务运行状态。对每个可执行的子任务模块，其数据结果的设计如下：
*TaskRecord ：*
```python
task = {
    "id": 1,
    "subject": "Write parser",
    "description": "",
    "status": "pending",
    "blockedBy": [],
    "blocks": [],
    "owner": "",
}
```
每个字段都对应一个很实用的问题：
| 字段 | 类型 | 说明 |
| :--- | :--- | :--- |
| `id` | int | 自增主键，文件名格式为 `task_{id}.json` |
| `subject` | string | 任务标题，创建时必填 |
| `description` | string | 任务详细描述，可选 |
| `status` | string | 任务状态：`pending` / `in_progress` / `completed` / `deleted` |
| `blockedBy` | int[] | 阻塞当前任务的任务 ID 列表（我依赖谁） |
| `blocks` | int[] | 被当前任务阻塞的任务 ID 列表（谁依赖我） |
| `owner` | string | 任务负责人，可由队友认领 |

* 其中的 `Status`，这里只保留最少 4 个状态，解释如下：

```
[ ] pending    - 待处理，尚未开始
[>] in_progress - 进行中，正在执行
[x] completed  - 已完成，触发依赖自动清理
[-] deleted    - 已删除
```
这4个状态是存在强的先后顺序，具体如下：
| 转换 | 触发条件 |
| :--- | :--- |
| `pending` → `in_progress` | 调用 `task_update` 设置 `status="in_progress"` |
| `in_progress` → `completed` | 调用 `task_update` 设置 `status="completed"` |
| `pending` → `in_progress` | 即使仍有 `blockedBy` 也可转换（不强制阻塞检查） |
| 任意 → `deleted` | 调用 `task_update` 设置 `status="deleted"` |

* 另外一个重点是：blockedBy 与 blocks 的双向关系
当某个任务id通过 Blocks 声明"我阻塞谁"时，系统会自动在对方任务的 blockedBy 中添加当前任务 ID，实现双向同步。

那么对应一个任务id的结构体来说，一个是否能开干的关键规则就是：
```python
def is_ready(task: dict) -> bool:
    return task["status"] == "pending" and not task["blockedBy"]
```

每一个任务id的数据结构在生成好以后需要让任务落盘，不要只把任务放在 `messages` 里，在磁盘上是“一任务一文件”：

```text
.tasks/
  task_1.json
  task_2.json
  task_3.json
```

## 3. 任务系统的具体实现

整个的数据结构和运行方式我们讲完了，下面看一下代码如何实现。

整个task类其实也是一个标准的包含CRUD（Create、Read、Update、Delete）操作方法的类。弄清楚了这些方法的构造过程也就清楚了代码实现。

对于大模型agent而言，具体到这个Task各个过程被触发的方式，都是通过**建设Tools工具**来实现的。那么大模型在理解任务、分配任务的过程中，来调用对应的工具，实现对于Task的执行。

类的完整实现较长，可以参考教程代码中的明细，这里列举一些主要的函数看看实现：

```
class TaskManager:
    """
    持久化任务存储管理器（任务图存在磁盘上）
    核心作用：管理任务的创建、查询、更新、列表、依赖关系，所有任务以 JSON 文件持久化保存
    """

    def create(self, subject: str, description: str = "") -> str:
        """
        创建新任务（C - Create）
        返回：创建好的任务JSON
        """
        task = {
            "id": self._next_id,          # 任务ID
            "subject": subject,           # 任务标题（必填）
            "description": description,   # 任务描述（可选）
            "status": "pending",          # 初始状态：待处理
            "blockedBy": [],              # 依赖的任务ID（我等谁完成）
            "blocks": [],                 # 被我阻塞的任务ID（谁等我完成）
            "owner": "",                  # 负责人
        }
        self._save(task)
        self._next_id += 1
        return json.dumps(task, indent=2, ensure_ascii=False)

    def get(self, task_id: int) -> str:
        """查询单个任务详情（R - Read）"""
        return json.dumps(self._load(task_id), indent=2, ensure_ascii=False)

    def update(self, task_id: int, status: str = None, owner: str = None,
               add_blocked_by: list = None, add_blocks: list = None) -> str:
        """
        更新任务（U - Update）
        支持：状态、负责人、依赖关系、阻塞关系更新
        任务完成时自动清理依赖（双向同步）
        """
        task = self._load(task_id)

        # 更新负责人
        if owner is not None:
            task["owner"] = owner

        # 更新状态
        if status:
            if status not in ("pending", "in_progress", "completed", "deleted"):
                raise ValueError(f"无效状态: {status}")
            task["status"] = status

            # 关键：任务完成 → 自动清理所有任务对它的依赖
            if status == "completed":
                self._clear_dependency(task_id)

        # 添加依赖关系（我依赖哪些任务）
        if add_blocked_by:
            task["blockedBy"] = list(set(task["blockedBy"] + add_blocked_by))

        # 添加阻塞关系（我阻塞哪些任务）→ 双向同步
        if add_blocks:
            task["blocks"] = list(set(task["blocks"] + add_blocks))
            for blocked_id in add_blocks:
                try:
                    blocked = self._load(blocked_id)
                    if task_id not in blocked["blockedBy"]:
                        blocked["blockedBy"].append(task_id)
                        self._save(blocked)
                except ValueError:
                    pass

        self._save(task)
        return json.dumps(task, indent=2, ensure_ascii=False)

    def list_all(self) -> str:
        """列出所有任务（格式化展示状态、负责人、依赖）"""
        tasks = []
        for f in sorted(self.dir.glob("task_*.json")):
            tasks.append(json.loads(f.read_text()))

        if not tasks:
            return "暂无任务"

        lines = []
        for t in tasks:
            # 状态图标
            marker = {
                "pending": "[ ]",
                "in_progress": "[>]",
                "completed": "[x]",
                "deleted": "[-]"
            }.get(t["status"], "[?]")

            # 显示依赖
            blocked = f" (依赖: {t['blockedBy']})" if t.get("blockedBy") else ""
            # 显示负责人
            owner = f" 负责人={t['owner']}" if t.get("owner") else ""

            lines.append(f"{marker} 任务{t['id']}: {t['subject']}{owner}{blocked}")

        return "\n".join(lines)
```

每个函数的实现其实非常清晰。
